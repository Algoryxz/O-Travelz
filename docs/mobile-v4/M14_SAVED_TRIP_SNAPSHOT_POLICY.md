# O-TRAVELZ Mobile V4 — Saved Trip Snapshot Policy

> **Authoritative Specification: Immutability and State Preservation for Persisted Itineraries**  
> Wave: `M14` | Status: `APPROVED_POLICY` | Date: `2026-09-08`  
> Policy: **`SAVED_TRIP_IS_IMMUTABLE_GENERATED_SNAPSHOT`**

---

## 1. The Immutability Axiom

A trip generated by the O-TRAVELZ itinerary solver (`POST /itinerary/plan`) is valid and optimal for the specific parameters, catalog state, and heuristics at the exact moment of generation. 

Once saved by the traveler:
1. **The persisted itinerary becomes an immutable historical snapshot.**
2. It must **never** silently recalculate, re-rank stops, swap destinations, or modify timings simply because:
   - The backend ranking weights were tuned.
   - A place's popularity or rating changed.
   - Mo Bus timetable schedules were updated.
   - Weather observations changed.
   - A new catalog version was deployed.
3. The itinerary only changes if the traveler explicitly taps **"Regenerate Plan"** or **"Update Itinerary"**.

---

## 2. Preserved Snapshot Attributes

To guarantee faithful offline and future rendering, a `SavedTrip` snapshot preserves:

| Dimension | Attribute | Purpose / Invariant |
|---|---|---|
| **Provenance** | `generatedAt: Long` | Epoch millisecond timestamp of generation. |
| **Schema Version** | `schemaVersion: Int` | Version identifier (starts at 1) for future migration. |
| **Constraints** | `constraintsSnapshotJson` | Exact JSON serialization of `PlanConstraints` (days, pace, interests, startHub, transport preferences). |
| **Summary & Grounding**| `title`, `aiExplanation` | Generated title and grounded AI explanation captured at creation time. |
| **Day Partitions** | `dayNumber: Int` | Explicit 1..7 sequence grouping stops and hops. |
| **Stop Order** | `stopSequence: Int` | Deterministic 1..3 sequence within each day. |
| **Stop Identity** | `canonicalPlaceId: String` | Immutable reference to canonical catalog place. |
| **Time Windows** | `plannedArrival`, `plannedDeparture` | Time-slot strings (e.g. `"09:00"`, `"11:00"`) returned by backend. |
| **Hop Presentation** | `mode`, `minutes`, `detail` | Connection attributes (e.g. `"walk"`, `15`, `"Walk ~200m"`, `"bus"`, `35`, `"Mo Bus Route 10"`). |
| **Hop Fare Truth** | `fare: null` | Strictly `null`. Never replaced by estimated or boarding guesses. |

## 3. Transient & Dynamic Data Handling

### 3.1 Live Weather Policy
- Live weather is transient and fleeting.
- Live weather observations shown during planning are **never** persisted as future weather predictions.
- The saved itinerary displays current weather only if live network connectivity is present and the active day matches the current calendar day; otherwise, weather is omitted or rendered as a calm `"Weather Unavailable"` badge.

### 3.2 Transit Telemetry Policy
- Saved hops preserve the scheduled transit route number and scheduled duration estimated at planning time.
- Saved hops **never** store live vehicle tracking, vehicle coordinates, or dynamic countdowns.
- When executing the trip, live timetable lookups may enrich the view if connected, but the snapshot base remains immutable.

### 3.3 Missing Canonical Place Resilience
If a place referenced by `canonicalPlaceId` is removed or modified in a future catalog update:
- The saved stop continues to render using its frozen `placeName` and `category` snapshot.
- A subtle indicator explains: *"This destination is from a prior catalog version."*
- The app **never** silently substitutes a different destination by name.
